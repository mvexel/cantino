# Cross-platform parity corpus

iOS done-criterion: **iOS and Android behave identically: same output on the
same input.** This directory makes that testable. One ordered list of calls
(`calls.json`) runs on every platform; each platform's runner maps its results
into one canonical JSON form and must reproduce `expected.json` **byte for
byte**.

| Runner | Status | Drives |
|---|---|---|
| Rust, `tests/parity.rs` | done, part of `cargo test` (so `scripts/check.sh`) | the C ABI (`include/cantino.h`) as a foreign caller |
| Kotlin, `ParityTest` in `android/cantino` androidTest | done (219 calls run, 24 `abi_only` skipped) | the public Kotlin API (`OsmStore`, `PmtilesInfo`), internal `SliceProtocol`/`AreaStorage`/`Failures`/`NativeBridge` where none exists; `PmtilesInfo` now carries every `basemap_info` field |
| Swift, `swift/Tests/CantinoTests/ParityTests.swift` | done, part of `scripts/swift-test.sh` | the public Swift API (internal `SliceProtocol`, basemap plan/assembler, `AreaStorage` and `Failures` for the slice, engine, area and failure ops); 219 run, 24 `abi_only` skipped |

The C ABI's own JSON, canonicalised, is the reference: `expected.json` is
generated by the Rust runner. Regenerate it only after an intended behaviour
change and review the diff (one line per call, so the diff names every call
whose behaviour changed):

```sh
UPDATE_PARITY=1 cargo test --test parity
```

| `../fixtures/area-storage-0.2.0/` | Area store directories as Cantino 0.2.0 left them (published, pending commit, half rolled forward, killed before the commit point, ...), for the area ops. Placeholder data files; a mobile runner bundles the tree, dot-directories (`.staging`) included. |

Area 1 is the existing `tests/fixtures/snapshot.osm` (imported three times:
default options, `preserve_untagged_metadata`, and as `snapshot.osm.pbf`). The
basemap ops use `tests/fixtures/basemap/slc-nw-z12-15.pmtiles`. Everything is
imported at run time; no `.sqlite` file is committed.

## Calls

Each call is `{"id","op","args"}` plus an optional `"abi_only": true`.

* `id` is unique, and is the key into `expected.json`.
* `args` is per op (table below).
* **Paths**: `scratch:<name>` is `<name>` inside a fresh, empty directory the
  runner creates for the run (imports write there; `scratch:missing.sqlite`
  never exists). Every other path is relative to the repository root; a mobile
  runner bundles those files (as assets/resources) and maps the path.
* **Areas**: `open` names a handle (`"area":"snapshot"`); later calls refer to
  it by that name; `close` ends it. Every area opened is closed by the end.
* **JSON arguments** (`request`, `bbox`, `options`): an object or array is the
  structured value (a typed runner builds its native type from it: `Query`,
  `List<OsmId>`, `Bbox`, `ImportOptions`); a **string** is raw text handed over
  verbatim (malformed input); `null` is a NULL pointer / absent value.
* **Kinds** are the ABI codes: node 0, way 1, relation 2.
* **`abi_only`** marks calls a typed platform API cannot express (NULL
  pointers, an invalid kind code, malformed or unknown-shape JSON for a typed
  argument, unknown import options). A platform runner **skips** them, and
  compares the remaining lines only (the Rust runner, being the ABI, runs all).
  Skipping is decided by this flag alone, never per runner.

| `way_coordinates` | `area`, `id` | `cantino_way_coordinates` |

| `area_recover` | as `area_published` | copy `fixture` to `root`, `cantino_area_recover`; see "Area ops" |

### Area ops

`area_published` and `area_recover` run on a copy of a directory from
`tests/fixtures/area-storage-0.2.0/` (laid out exactly as Cantino 0.2.0's
Kotlin `AreaStorage` left it; scenarios are described in
`tests/area_storage.rs`), so they are deterministic and touch no committed
file. The runner copies `fixture` (recursively) to `root`, which must not
exist yet (each call names its own); with a null `fixture`, `root` stays
absent. The result is `{"result": <outcome>, "files": <listing>}`:

* `result`: the call's outcome, with every string that is a path under
  `root` rewritten relative to it (`root` itself becomes `"."`; separator
  `/`). `area_layout` applies the same projection to its outcome.
* `files`: every regular file under `root` after the call, as an object from
  relative path (`/`-separated) to size in bytes, or `null` when `root` does
  not exist. It shows what recovery moved, deleted and left (the empty
  `city.lock` the core creates, a dead run's staging directory).

`basemap_extract` plays the HTTP server by slicing the local `source` file (a
range past the end comes back short, as from a server) and records every
engine answer in this fixed order, so every runner makes the same calls:

1. `plan_new` (must succeed), `first_request` → `first_request`.
2. FIFO queue starting with the first request: pop the front, `plan_feed` it,
   append `{"id", "step"}` to `feeds`. A `{"fetch":[...]}` step appends its
   ranges to the back of the queue; `"wait"` continues; `{"tiles_ready":...}`
   or an error stops the loop.
3. `plan_outstanding` → `outstanding`.
4. If the loop did not end in `tiles_ready`: `plan_free` → `free`; the result
   is `{"first_request","feeds","outstanding","free"}`.
5. Otherwise: `plan_into_assembler(staging = scratch:basemap.part)` →
   `into_assembler`; `asm_remaining` → `remaining`; `asm_progress` →
   `progress_before`; `asm_finish(scratch:basemap.pmtiles)` with nothing
   written → `finish_early` (must be refused); `asm_write_range` for every
   range of `remaining`, in that order → `writes` (array of outcomes);
   `asm_progress` → `progress_after`; `asm_finish` → `finish`; `asm_free` →
   `free`; `basemap_info` on the output → `info`.

## Outcomes

Every ABI call's result becomes one of:

| Native result | Canonical outcome |
|---|---|
| status 0 with result JSON | `{"ok": <the JSON>}` |
| status 0 without result JSON (`open`, `close`, `plan_new`, `asm_write_range`, `asm_finish`, `*_free`) | `{"ok": null}` |
| status 1 (nothing to return: object not in the area for `get`, `way_coordinates`; no published area for `area_published`; not a failure for `classify_failure`) | `{"missing": true}` |
| negative status | `{"error": {"code": N, "kind": "<name>"}}` |

The error `code` is the negated status (`-CANTINO_ERROR_*`), and `kind` its name: 1 `invalid_argument`, 2 `invalid_file`,
3 `io`, 4 `wrong_thread`, 5 `internal`. **The error message is not part of the
outcome**: messages are for developers and not a contract. A Kotlin runner
maps exception classes (`CantinoException.InvalidArgument` → 1
`invalid_argument`, ...; the subclass is chosen from the same code in
`src/android.rs`); Swift maps its error enum the same way. A `null` returned
by `get`/`wayCoordinates` is `{"missing":true}`.

Two deliberate projections, applied by every runner:

* `import`: `database_bytes` is **dropped** from the report (only `counts`
  stays). It is SQLite's page allocation, not a behaviour contract.
* `basemap_info`: the full C ABI object (including `spec_version`, `center`,
  `tile_type`, `tile_compression`, `clustered`), which `PmtilesInfo`
  exposes on both platforms.

The Rust runner also asserts the buffer contract on every call: a result
buffer only with status 0 and an error message (non-empty) exactly with a
negative status.

## Canonical form

A canonical value is UTF-8 JSON written as follows. The C ABI's JSON parsed
and re-written by these rules is the reference; a platform runner writes its
own native values (objects, lists, numbers) with the same rules. Native types
map to the C ABI shapes (`Node` → `{"type":"node","id","coordinate":{"lat_e7",
"lon_e7"},"location_version","tags","metadata"}`, way `nodes`, relation
`members` `[{"id":{"type","id"},"role"}]`, `metadata` `{"version",
"timestamp","changeset","uid","user"}` or `null`, `Coordinate` →
`{"lat_e7","lon_e7"}`, a way-coordinate list → the flat `[lat_e7, lon_e7,
...]` array with `null, null` for a node outside the area).

1. **No insignificant whitespace**: no spaces or newlines between tokens.
2. **Object keys sorted by Unicode code point** (equivalently, by UTF-8
   bytes). Not by UTF-16 code unit: Java/Kotlin `String.compareTo` and
   `TreeMap<String,_>` sort `😀` (U+1F600, UTF-16 `D83D`) before `ｚ`
   (U+FF5A); code point order is the reverse. Node 20 of `geometry.osm`
   exists to catch this. Compare with `codePoints()` (Kotlin) or
   `unicodeScalars` (Swift).
3. **Strings**: `"` and `\` escaped as `\"` and `\\`; U+0008 `\b`, U+0009
   `\t`, U+000A `\n`, U+000C `\f`, U+000D `\r`; other U+0000..U+001F as
   `\u00XX` with lowercase hex; **nothing else escaped**: `/` stays `/`
   (org.json writes `\/`) and non-ASCII stays raw UTF-8 (never `\uXXXX`).
4. **Integers** in plain decimal, as-is (IDs up to 2^63-1, u32 metadata,
   byte counts). Every coordinate in an output is already an integer e7
   value (`lat_e7`, `lon_e7`, the flat way-coordinate array).
5. **Floats** (fields that are floating point in the C ABI: `fraction` of
   `slice_progress`; `bounds`/`center` of `basemap_info`) are written as the
   shortest decimal that round-trips to the same IEEE-754 double, **always
   with a fraction or exponent**: `1.0`, `0.25`, `-112.09`, `12.0`,
   `0.3333333333333333`. This is serde_json's (ryu) output; for magnitudes
   from 1e-5 up to 1e16 it is plain decimal, which is all the corpus uses.
   Kotlin/Java `Double.toString()` is not guaranteed shortest on every
   runtime (older JDKs and Android libcore versions differ) and switches to
   `E` notation below 1e-3 and from 1e7; Swift's `description` is shortest
   but has its own exponent thresholds. Runners format floats explicitly
   rather than trusting the platform default. A float field is
   written as a float even when integral (`12.0`, never `12`): org.json's
   `JSONObject.toString` drops the `.0` and must not be used for output.
6. `true`, `false`, `null` as literals. Optional values the ABI writes as
   `null` (`metadata`, `fraction`, `size_bytes`, `timestamp`, missing batch
   entries) are written as `null`, never omitted.
7. String values that are themselves JSON (the `body` of `slice_job_request`)
   are compared as strings, verbatim: the adapter POSTs them unchanged.

## Result file

`expected.json` (and what every runner produces) is:

```
[
{"id":"<first id>","result":<canonical outcome>},
...
{"id":"<last id>","result":<canonical outcome>}
]
```

`[` + `\n`, then one canonical `{"id","result"}` object per call in
`calls.json` order joined by `,\n`, then `\n]\n`. It is valid JSON and
diffable line by line. A runner that skips `abi_only` calls drops those
lines from `expected.json` (by id) and compares the rest, byte for byte.

## Writing a platform runner

1. Load `calls.json`; create a fresh scratch directory; make the
   repository-relative files available (bundle `tests/fixtures/...` and
   `tests/parity/*.osm`).
2. For each call without `abi_only`, in order: run the op through the
   **public** platform API (fall back to the internal bridge only where the
   public API has no equivalent, and say so in the runner), catch the
   platform's typed error, and build the canonical outcome.
3. Write the result file as above and compare it byte for byte with
   `expected.json` minus the `abi_only` lines. On mismatch, report the
   differing ids. Never regenerate `expected.json` from a platform runner:
   the C ABI is the reference; a platform difference is a platform bug (or a
   reason to change the core and regenerate from Rust).
4. All calls on one area run on the thread that opened it (handles are
   thread-confined), except `get_from_other_thread`.

### WrongThread

`get_from_other_thread` uses the area's handle from a freshly spawned thread
and expects `{"error":{"code":4,"kind":"wrong_thread"}}`; the next call
(`get.snapshot.after_wrong_thread`) shows the handle is untouched. It is
deterministic given a second thread, but depends on the runner owning the
handle on its opening thread: a runner that only reaches the store through a
thread-hopping wrapper (Kotlin `AsyncOsmStore`, a Swift actor) must use the
synchronous store type for this call.

### Op → platform API

Kotlin names are from `android/cantino` at the time of writing (the package
is being renamed; the class names are what matter). Swift names are a
proposal for the adapter, mirroring Kotlin.

| op | Kotlin API | Swift API (planned) |
|---|---|---|
| `import` | `OsmStore.importArea(input, destination, ImportOptions)` → `ImportReport` | `OsmStore.importArea(input:destination:options:)` → `ImportReport` |
| `open` | `OsmStore.open(path)` | `OsmStore(path:)` (throwing init) |
| `close` | `OsmStore.close()` | `OsmStore.close()` |
| `get` | `OsmStore.get(OsmId)` → `OsmObject?` | `OsmStore.get(_ id: OsmId)` → `OsmObject?` |
| `get_from_other_thread` | `OsmStore.get(OsmId)` from a new `Thread` → `CantinoException.WrongThread` | `OsmStore.get(_:)` from a new `Thread` → `CantinoError.wrongThread` |
| `get_many` | `OsmStore.get(ids: List<OsmId>)` → `List<OsmObject?>` | `OsmStore.get(_ ids: [OsmId])` → `[OsmObject?]` |
| `query` | `OsmStore.query(Query)` | `OsmStore.query(_ query: Query)` |
| `way_coordinates` | `OsmStore.wayCoordinates(wayId)` → `List<Coordinate?>?` | `OsmStore.wayCoordinates(_ wayId: Int64)` → `[Coordinate?]?` |
| `slice_job_request` | `SliceProtocol.jobRequest(base, Bbox, name)` (internal) | `SliceProtocol.jobRequest(base:bbox:name:)` (internal) |
| `slice_job` | `SliceProtocol.job(base, response)` (internal) | `SliceProtocol.job(base:response:)` (internal) |
| `slice_progress` | `SliceProtocol.progress(status)` (internal) | `SliceProtocol.progress(status:)` (internal) |
| `basemap_info` | `PmtilesInfo.read(File)` (subset) + `NativeBridge.basemapInfo` for the rest | `PmtilesInfo.read(_ url: URL)` (all fields) |
| `basemap_plan_new`, `basemap_bad_feed`, `basemap_extract` | `NativeBridge.basemapPlan*` / `basemapAsm*` (internal; the public path, `BasemapExtract.run`, does its own HTTP and cannot be fed canned bytes) | the internal plan/assembler wrapper under the Swift `BasemapExtract` |
| `area_validate_id` | `AreaStorage.requireValidAreaId(areaId)` (internal; `IllegalArgumentException` → `invalid_argument`) | `AreaStorage.validate(areaId:)` (internal, throws `CantinoError.invalidArgument`) |
| `area_layout` | `NativeBridge.areaLayout(root, areaId, workId)` (internal; `AreaStorage` exposes only single paths) | `AreaStorage(root:).layout(areaId:workId:)` (internal; `workId` as raw text so a malformed one reaches the core) |
| `area_published` | `AreaStorage(areas = root, downloads = scratch).published(areaId)` → `AreaInfo?` (internal; map `AreaInfo` back to `{"data","basemap","metadata"}` with `AreaMetadata.toJson` key names) | `AreaStorage(root:).published(areaId:)` → `AreaInfo?` (internal; `AreaInfo.canonical`) |
| `area_recover` | `NativeBridge.areaRecover(root, areaId)` (internal; `AreaStorage.recover` swallows I/O errors by design) | `AreaStorage(root:).recover(areaId:)` (internal) |
| `classify_failure` | `NativeBridge.classifyFailure(input)` (internal; `Failures` wraps it, and the runner checks class and reason of `Failures.http`/`io` against it) | `Failures.classify(_ input: Failures.Input)` (internal) |

Errors: Kotlin `CantinoException.{InvalidArgument, InvalidFile, Io,
WrongThread, Internal}`; Swift (planned) `CantinoError.{invalidArgument,
invalidFile, io, wrongThread, internal}`, each mapped to its `code`/`kind`.

## Not covered, and why

* `cantino_free` is not an op; every call uses it (the Rust runner frees
  every buffer).
* `cantino_basemap_asm_write_range_file`: streaming from a file is
  platform I/O, and its result is identical to `write_range` by design;
  covered by `scripts/mobile-api-smoke.py` and the Rust tests.
* Basemap `"fetch"`/`"wait"` steps: the committed PMTiles fixture has no leaf
  directories, so the plan is ready after the first response. Exercising the
  multi-step path needs a committed leaf-directory fixture (the synthetic
  archives of `tests/basemap.rs` are built in code, which every runner
  would have to re-implement).
* `Store::dependencies`: not exposed through the C ABI, so not a platform
  behaviour yet.
* The `Internal` error kind: only a core bug or a caught panic produces it;
  there is no deterministic input for it (covered by `src/mobile_api.rs`
  unit tests).
* A `get_many` of exactly 10000 IDs (the cap) succeeds; left out because its
  expected line would be about a megabyte. Over the cap (10001) is covered.
* Areas from a SliceOSM download or a basemap from the network: online, not
  deterministic.
